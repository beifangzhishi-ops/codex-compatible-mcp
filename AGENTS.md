# Repository Instructions

- **Codex 上游优先（项目铁则，最高架构优先级）**：除 ChatGPT/GPT Host 专属的接入、MCP App/UI、OAuth/插件传输适配外，CCM 的所有对外执行语义、命令及 Shell 解析、审批决策、持久授权、规则格式、沙箱与权限、子进程环境、配置行为、错误语义、会话生命周期和工具行为，均必须直接以 OpenAI Codex 上游真实代码为规范。不得凭记忆、推测或自行设计“类似 Codex”方案，也不得只借鉴部分设计后加入未经用户批准的差异。
- **先查上游、后改 CCM**：每次改动上述非 Host 行为前，必须查看并记录 Codex 上游对应实现、准确 commit SHA、具体源码位置及适用平台，并建立逐项行为对应和测试。优先移植上游真实实现；CCM 使用不同语言/Controller–Worker 架构时，只允许保持同等语义的必要适配。上游没有的功能、无法移植的行为、对原有 CCM 功能的取舍、任何拟议差异或历史兼容需求，必须事先明确询问用户；不允许擅自创造替代规则或悄悄保留旧方案。
- **完整性与验收**：涉及某个 Codex 子系统时，应覆盖该子系统完整的关键决策链及边缘情况（解析→授权→执行→持久化→回执等），而不只是修补当前案例；测试必须以同一固定上游 commit 的行为为准。维护 README 的上游基准、覆盖范围、未对齐项和已获用户批准的差异；不得把未验证的实现称为“已完整对齐 Codex”。本铁则优先于本文件中此前任何相冲突的 CCM 专有实现说明；发现冲突应先报告并按用户决定清理，而非借旧规则自行决定。
- 完整对齐清单见 `docs/codex-parity.md`；非 GPT Host 行为的每次相关变更必须更新模块状态、上游源码路径、验证证据及未解决差异，不得用某个模块测试通过代替全项目对齐验收。

- Do not change the directory structure of tools without explicit user permission.
- When investigation confirms a client, Host, model, or Worker compatibility issue, record the current compatibility constraint, affected surface, and required routing or workaround in README.md as part of the same change. Remove obsolete compatibility wording when the constraint no longer applies.
- Keep model-facing Plan behavior synchronized across Controller instructions, the Plan tool descriptions, README.md, and their contract tests; remove superseded Plan guidance instead of retaining parallel historical rules.
- The Direct + Code Mode `ccm-extra.publish` tool accepts either `plan_id` alone for a complete immutable Controller Plan snapshot, or `workspace_handle` plus `path` for a Worker file, never both. Markdown publications show a bounded rendered excerpt in the MCP App and full isolated HTML preview, but always download the original Markdown bytes. On Plan completion publish the latest persisted Plan and summarize it briefly rather than copying the full text into chat; publishing does not authorize implementation. Reuse the shared file cache and MCP App, report publish failures, and remove stale tool names.
- Keep the CCM Git versions on 6v (Controller host) and noha (Remote Worker) synchronized for each completed CCM update. After changes are tested and committed/pushed from 6v, update noha to the same exact commit using a fast-forward-only pull, then restart the affected CCM services/Worker through their existing supervisors and verify both `git rev-parse HEAD` values match and both environments reconnect normally. Do not overwrite local changes on either host; if either update, restart, or verification is blocked, report the version mismatch explicitly instead of calling the rollout complete. An intentionally staged rollout requires the user's explicit direction.
- CCM routine restart authorization is action-specific: use the Deferred `ccm.restart` capability, exact registered environment identity and `config/restart-allowlist.json`; never implement restart trust as a generic shell/executable/token-prefix rule. Only a supervised CCM instance can restart, and acceptance is not proof of recovery. Verify health and reconnection afterward.
- Built-in command trust is configured in `config/trusted-commands.json`, read by the Controller at every new exec dispatch. Model edits are allowed. Keep executable, argument, platform and Shell selectors in config; keep the parser, executable rewriting and execution routing in code. No restart is needed for rule edits; invalid/missing configuration disables built-in auto-trust for the request.
- Only grant compound-script trust when every command segment matches a rule, preserving Shell operators and literal executable path bindings; reject unsupported syntax, pipelines, computed targets and ambiguous CMD rewriting. The Worker must not independently elevate Git or any other command class. On restricted Tailscale pipe denial include a brief rule-configuration hint in initial/polled outputs, but do not emit it for ordinary successes or unrelated errors.
- User-approved Always allow decisions save Controller-wide command token prefixes. Match these rules on ordinary exec_command requests before the first sandboxed attempt, as well as explicit escalations, without binding Worker, workspace, workdir, Shell, or TTY. Match every executable segment of a compound command. Keep frozen per-command approval and independently configured hash-bound package-script trust distinct from this global allowlist. The approval card must show its global scope.
- Keep both the Controller introduction and exec_command description advising models to proactively propose a narrow reusable prefix_rule for recurring build/test/dev commands requiring escalation, retaining stable program, subcommand, script path, and invariant flags while excluding variable suffix arguments. Never suggest bare general-purpose shells or interpreters. The card must expose the exact global prefix for the user's Always allow decision.
- Worker child-command CA configuration belongs in each machine's ignored `config/worker.env`, alongside `CCM_*` bootstrap settings. `CURL_CA_BUNDLE` is loaded before the upstream Codex shell environment policy so Codex `set` may override or filter it. Do not alter global certificate verification or expose Controller/WorkerHub/OAuth secrets to that config.
- On Windows, new user commands must refresh Machine/User registry environment variables and combine PATH in system-before-user order for pipe, PTY, restricted and approved execution; Supervisor/Controller/Worker environments remain stable. Protect CCM_* runtime controls, then apply the existing child proxy policy and validated CA override. Fail visibly on registry read errors rather than reverting to stale PATH.

- `exec_command(run_as_admin=true)` is an experimental Windows workspace-write command path, not Full Access: keep its Controller validation, Worker `admin-workspace-write` native helper, no implicit Always allow trust, and tests of admin SID / workspace and external writes. Do not change the Worker default permission profile or add an experiment switch. Reject grant / escalation / prefix combinations and non-elevated Workers. Its restricted SID may prevent administrator service/process operations; do not describe this as a complete OS isolation boundary or reliable service-admin method.
- Never restore all administrator privileges to the experimental restricted token while claiming workspace write confinement. A 6v probe showed that enabling SeRestorePrivilege and opening an outside file with FILE_FLAG_BACKUP_SEMANTICS bypassed WRITE_RESTRICTED and modified the file, even when normal Set-Content and icacls failed. A strictly enforced boundary for unrestricted administrator commands needs an additional trusted enforcement layer; token ACLs alone do not suffice. The current mode also cannot change ACLs inside the workspace with icacls because its capability SID lacks WRITE_DAC.
- Registered-project `select_workspace` / `register_workspace` are Deferred + Code Mode; discover through `tool_search` and invoke through `exec` only with explicit user authorization and no usable handle. Return the real `workspace_handle` unchanged without binding a UI to those action tools. After full-access success, call the read-only `show_workspace_handle` Direct tool to show the validated handle through CCM's copyable MCP App; for restricted actions the completed approval card displays it. Do not rely on the model to reproduce handles in prose, do not publish handles for `create_projectless_handle`, and do not show handles for rejected/failed/pending actions. Keep the model-facing handle handoff and frozen approval semantics intact.
- An existing `workspace_handle` supplied by user/project instructions or CCM must be reused directly for the matching workspace. It is not an `environment_id`, `workspace_id`, or conversation context; do not select/register/create projectless or request entry approval again merely to fetch a fresh handle. Multiple valid handles may reference the same registered project.
- Workspace selection requires both an absent/unusable handle and an explicit user request to enter/switch workspaces; registration requires an explicit user request to register and no usable handle. Reading, inspecting, editing, or working on a project (including saying "read the workspace") never authorizes entry, registration, or workspace-entry approval. Missing/invalid handles are not permission to enter automatically. Projectless handles may be used for permitted absolute-path reads, not to bypass pending entry approvals or write into registered projects.
- `create_projectless_handle` is Direct + Code Mode for genuinely projectless operations without an available handle. Reuse a supplied projectless handle instead of creating another, and never use a projectless handle to bypass a pending registered-project entry approval.
- Approval App remounts must restore terminal state and entered-workspace handle without repeating any frozen action or follow-up. Querying archived receipts requires the original card nonce and must be read-only; never restore a consumed approval as executable. Treat optional Host widgetState as a display cache, not authority.
- Registered-project unregister must always use a one-shot approval card, even on full-access Workers. Read and revalidate Worker-local registration identity even if its directory is missing; do not weaken select/exec directory validation. Revoke existing handles, preserve project directories/files, and never auto-reseed deliberately unregistered bootstrap entries.
